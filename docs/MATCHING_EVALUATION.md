# План сравнения matching

## Изолируем сравниваемую часть

Обе версии получают один и тот же заранее зафиксированный JSON распознавания
(`status`, `meal_name`, `brand`, `items[].name/brand/amount_g`). Это отделяет
качество matching от случайности распознавания фото. Ни одна версия не вызывает
создание записи в дневнике. Порядок примеров перемешивается, а версия алгоритма
скрывается от человека, который выставляет оценку.

Локальный набор состоит только из синтетических ответов FatSecret с вымышленными
ID. Для каждой карточки фиксируются название, бренд, несколько порций и КБЖУ.
Ожидаемые `candidate_ref`, `serving_ref`, масса и решение `ok/uncertain`
описываются до запуска.

В синтетических fixtures бренд и КБЖУ задаются искусственно; таблица не утверждает
наличие конкретного `food_id` в реальном каталоге. Для реального сравнения
эталонную позицию, порцию и доступность каталога нужно проверить вручную перед
запуском и не придумывать отсутствующие ID.

## Метрики

Для каждого примера фиксируются:

* точный выбор продукта: 1/0 по заранее заданному эталону;
* точный выбор порции: 1/0;
* абсолютная и относительная ошибка массы;
* абсолютная ошибка calories/protein/fat/carbohydrate после пересчёта на массу;
* полнота компонентов составного блюда и число лишних компонентов;
* ошибочный уверенный выбор: `ok` при неверном продукте или порции;
* оправданный отказ и лишний отказ (`uncertain`);
* вызовы Gemini, FatSecret, tools и cache hits;
* длительность всей операции и каждого внешнего этапа;
* размер сериализованного контекста FatSecret, отправленного Gemini, в байтах.

Основные критерии принятия: новый вариант не ухудшает точность продукта, порции и
Brand-примеров; не увеличивает ошибочные уверенные выборы; отклонение КБЖУ после
масштабирования не хуже старой версии. Сокращение байтов и вызовов само по себе
не компенсирует ухудшение этих показателей.

## Локальный прогон

Добавьте fixtures к отдельному тестовому модулю и запускайте обе реализации на
одних объектах без сети. Отчёт содержит агрегаты и построчные различия, включая
отказы. Повторите прогон несколько раз: при фиксированных ответах результат
должен быть детерминирован. Текущие unit-тесты уже проверяют преобразование
карточек, бюджеты, происхождение ID и пересчёт порций; полноценный A/B baseline
потребует сохранить старую реализацию в отдельном checkout, а не возвращать её
в production-код.

## Будущая проверка с каталогом

Она требует отдельного разрешения на реальные read-only вызовы FatSecret и
Gemini и снятого юридического блокера передачи сокращённых данных. Создание
дневниковых записей должно быть отключено на уровне тестового harness.

1. Зафиксировать входные JSON распознавания и ручные эталоны до запуска.
2. В двух изолированных checkout выполнить старый и новый matching максимально
   близко по времени с одинаковым входом и лимитами.
3. Проверить выбранные продукты и порции вручную, затем посчитать метрики выше.
4. Не сохранять полные ответы API дольше разрешённого FatSecret срока. Если
   условия аккаунта не разрешают fixtures из ответов, хранить только допустимые
   агрегаты; для повторного прогона заново читать каталог.
5. Не писать в дневник и остановить прогон при приближении к квоте.
